# #384: Actions stuck `Executing` after server restart — root cause + fix design

Status: design draft, awaiting user authorization
Author: distributed-systems-reviewer
Created: 2026-05-10

---

## Confirmed mechanism (with file:line evidence)

The scheduler has **no scheduler-driven liveness sweeper for actions in
`Executing` stage**. Liveness is delegated entirely to per-action
`changed()` listener loops that live INSIDE the gRPC subscriber returned to
the caller (Bazel client or matching engine). When no such listener is
polling an action, the per-action 30 s timeout in
`MatchingEngineActionStateResult::changed`
(`nativelink-scheduler/src/simple_scheduler_state_manager.rs:184-252`) never
runs, and the action stays `stage=Executing` indefinitely with the worker's
keepalives keeping the worker (but not the action) alive in the registry.

Evidence chain:

1. **Listener-as-watchdog design.** Every per-action timeout decision is
   made inside `MatchingEngineActionStateResult::changed`
   (`simple_scheduler_state_manager.rs:184`). The function does
   `tokio::select { sub.changed() => ..., (now_fn).sleep(no_event_action_timeout) => check }`.
   On the sleep arm it calls `should_timeout_operation`
   (`simple_scheduler_state_manager.rs:350`) which returns true when the
   worker registry says the worker is dead OR when `max_executing_timeout`
   has elapsed. Production has `max_action_executing_timeout_s = 0` (default
   disabled, `simple_scheduler.rs:592`), and the wedged workers ARE alive,
   so this path can never fire.

2. **Listener creation is caller-driven.** The only code paths that
   instantiate the listener are:
   - `ClientStateManager::add_action`
     (`simple_scheduler_state_manager.rs:1104-1118`) — invoked when the
     Bazel client first calls `Execute`.
   - `ClientStateManager::filter_operations`
     (`simple_scheduler_state_manager.rs:1121-1132`) — invoked on
     `WaitExecution`.
   - `MatchingEngineStateManager::filter_operations`
     (`simple_scheduler_state_manager.rs:1166-1178`) — invoked from
     `do_try_match` BUT ONLY for `OperationStageFlags::Queued`
     (`simple_scheduler.rs:209-219` and again at 731), never for
     `Executing`. The one Executing-stage filter at
     `simple_scheduler.rs:793` is a `count()`-only call inside the stall
     detector — it does not subscribe.

3. **No periodic Executing sweeper.** A workspace search for
   `OperationStageFlags::Executing` in production code returns three
   hits, all in the scheduler crate, none of which iterate Executing
   actions to drive timeouts. The only `spawn!` in `simple_scheduler.rs`
   is `simple_scheduler_task_worker_matching` (line 615) which only
   processes Queued actions.

4. **Worker-side eviction does close the loop, but only when the worker
   itself disconnects or times out.** `WorkerConnection`'s disconnect
   handler (`worker_api_server.rs:1069-1071`) calls
   `scheduler.remove_worker(worker_id)`, which feeds into
   `immediate_evict_worker(worker_id, _, false)` →
   `running_action_infos.drain()` →
   `update_operation(_, UpdateWithError(_))` for each operation
   (`api_worker_scheduler.rs:1187-1193`). `UpdateWithError` re-queues the
   action up to `max_job_retries` times
   (`simple_scheduler_state_manager.rs:784-810`). Periodic sweeper
   `remove_timedout_workers` (`api_worker_scheduler.rs:3840-3962`,
   driven from `worker_api_server.rs:262-281` once per second) calls
   the same path with `is_disconnect=false` after `2 * worker_timeout_s`
   (60 s default). **None of these fire if the worker is healthy.**

5. **Production confirmation.** `journalctl --namespace=nativelink` for
   the wedged operation IDs shows them appear once in the
   `do_try_match` "Oldest actions in state" snapshot at 18:37:35.212 UTC
   with `last_transition≈4ms` (i.e. they had just transitioned to
   Executing) and never receive any further update. By 18:51:58, the
   snapshot still shows
   `client_operation_id=58323623-c0ce-4ea5-b548-fafa680035a4` with
   `last_transition=14m 23s`. No `WARN`/`ERROR` lines, no worker
   eviction, no `Worker not found in worker map` — the dispatch path
   succeeded at the channel level and then no party ever updated the
   action's state.

6. **Why "post-restart-dispatched cohort" specifically?** Bazel
   re-invoked `Execute` after the server restart (NEW operation_id was
   generated by `OperationId::default()` at `execution_server.rs:289`).
   The first `inner_execute` call returned a fresh stream to Bazel.
   Bazel's gRPC client is allowed to drop that stream and re-issue
   `WaitExecution(name=...)` later, but if for any reason it does NOT
   subscribe (e.g. it crashed, exited, was rate-limited, the connection
   broke during the brief restart window and Bazel gave up), then
   nothing is polling the `to_execute_stream` unfold loop
   (`execution_server.rs:216-246`). Without that loop polling
   `action_listener.changed()`, the `MatchingEngineActionStateResult`
   sleep-arm never runs and the timeout machinery never fires. New
   actions queued AFTER the restart had healthy Bazel clients with live
   ExecuteStreams, so their listeners drove timeouts normally.

   *(The user's working hypothesis was a worker boot_epoch wipe. That
   is not what happened: workers did not restart their boot_epoch — only
   the server bounced — and the boot_epoch wipe path
   (`worker_api_server.rs:520-600`) explicitly does not touch action
   state. The wipe only clears `locality_map`, `ac_pin_registry`, and
   `small_blob_dispatcher` per-endpoint state.)*

## State machine

```
                ┌──────────────────────────────────────────────────────┐
                │                                                      │
                │                                                      ▼
   ┌────────┐   │           ┌──────────┐         ┌─────────────────────────┐
   │ Queued │───┼───────────►Executing │────────►│ Completed/CompletedCache │
   └────────┘   │           └──────────┘         └─────────────────────────┘
       ▲        │                │ │
       │        │ UpdateWithErr  │ │  UpdateWithActionStage(Completed)
       │        │ (worker evict) │ │  via Worker→Server gRPC stream
       │        │ * max_retries  │ │
       └────────┘                │ │
                                 │ │
                                 │ │  worker keepalive observed
                                 │ │  (ScheduleStateManager::worker_keep_alive)
                                 │ │  → resets last_worker_updated_timestamp
                                 │ │     but keeps stage=Executing
                                 │ │
                                 │ ▼
                ┌────────────────────────────────────────────────┐
                │ ORPHAN PATH (#384): no client listener AND     │
                │ worker is healthy AND max_executing_timeout=0  │
                │                                                │
                │ Triggers:                                      │
                │   – Bazel disconnected and never re-issued     │
                │     WaitExecution                              │
                │   – `do_try_match` only iterates Queued        │
                │   – `should_timeout_operation` is unreachable  │
                │     from any background task                   │
                │                                                │
                │ Result: action stays Executing forever; worker │
                │ never sees a kill request; client gets no      │
                │ result; resource is locked indefinitely.       │
                └────────────────────────────────────────────────┘
```

## Composite invariant being violated

```
scheduler_thinks_executing
  ⇒ ( client_listener_polling          // Bazel WaitExecution stream open
      AND no_event_action_timeout fires within bound )
    OR
    ( worker_eviction_fires_within_2*worker_timeout_s )
    OR
    ( max_action_executing_timeout_s > 0
      AND elapsed > max_action_executing_timeout_s )
    OR
    ( scheduler_driven_executing_sweeper_fires_within_bound )  // <- DOES NOT EXIST
```

The first three corners can all be FALSE simultaneously in production today
(client gone, worker healthy, max_executing_timeout disabled). The fourth
corner does not exist. The composite is therefore unguarded.

## Fix proposals (rank-ordered by surface area + risk)

### Option A — minimum viable (recommended): scheduler-driven Executing sweeper

Add a periodic background task to `SimpleScheduler` (or
`SimpleSchedulerStateManager`) that, every `no_event_action_timeout / 2`
(default 15 s), iterates Executing actions and re-uses the existing
`should_timeout_operation` logic, calling `timeout_operation_id` on any
that fail it.

**Files to modify (estimated 60–100 LOC plus test):**
- `nativelink-scheduler/src/simple_scheduler.rs` — add second `spawn!`
  alongside `simple_scheduler_task_worker_matching` named
  `simple_scheduler_executing_sweeper`. Loop pattern: `interval` ticker,
  `weak_self.upgrade()` guard, `matching_engine_state_manager.filter_operations(OperationFilter { stages: OperationStageFlags::Executing, .. })`,
  iterate stream, for each call `should_timeout_operation` and
  `timeout_operation_id` if true.
- `nativelink-scheduler/src/simple_scheduler_state_manager.rs` — promote
  `should_timeout_operation` to public (it already is `pub`) and confirm
  `timeout_operation_id` (line 539) is callable from the new sweeper.

**Risk profile (LOW):**
- No protocol changes; no worker-side changes; no API surface changes.
- Reuses already-tested helpers (`should_timeout_operation` + worker
  registry liveness check).
- Duplicate firing (sweeper + listener both trigger timeout) is
  idempotent — the second `update_awaited_action` returns
  `Code::Aborted` from the version check
  (`simple_scheduler_state_manager.rs:849`) and is ignored.

**Composite invariants this fix interacts with:**
- Worker-keepalive freshness (untouched).
- Per-action timeout machinery (reuses `should_timeout_operation`).
- `max_action_executing_timeout_s = 0` semantics: today this means
  "rely on worker-registry liveness only." After fix this still holds —
  Option A simply ensures someone polls the existence of stale
  `Executing` actions instead of relying on the client to do it.

**Trip-wire check (CLAUDE.md "Composite admission/eviction/pin"):** N/A —
this is not a cache; it is a queue with a missing eviction rule. The
analogous mandate for queue-with-missing-sweeper is named explicitly in
the dead-letter audit section of the distributed-systems-reviewer
mandate. The wedged actions in `awaited_action_db.executing` are a
dead-letter set whose only consumer (the listener) is caller-driven.

---

### Option B — architectural: subscribe-on-Executing-transition

Change `assign_operation` (`simple_scheduler_state_manager.rs:1181-1195`)
to additionally register a server-internal subscriber on the awaited action
at the moment of Queued→Executing transition. The subscriber is a
self-driving `MatchingEngineActionStateResult`-equivalent that lives for
the duration of the Executing stage and is dropped on terminal transition.

**Files to modify (estimated 200–300 LOC plus tests):**
- `nativelink-scheduler/src/simple_scheduler_state_manager.rs` — new
  internal subscriber type, lifecycle wiring in `assign_operation`,
  drop hook on terminal transition.
- `nativelink-scheduler/src/memory_awaited_action_db.rs` — possibly need
  to ensure subscriber survives across `update_awaited_action` calls.
- Tests for subscriber lifetime (must not leak when actions complete).

**Risk profile (MEDIUM):**
- More invasive; touches the listener model.
- Requires careful drop-on-terminal logic to avoid leaking subscriber
  futures.
- Conceptually cleaner — the listener model becomes complete (every
  Executing action has an internal listener), making the wedge
  structurally impossible.

**Composite invariants:**
- Subscriber lifecycle MUST be exception-safe — drop on Completed,
  CompletedFromCache, AND on the worker-eviction path (else two
  drainers race).
- Memory cost: O(executing_count) live futures. For 64 workers × 32
  in-flight actions that is ~2048 futures, each ~few-KB — bounded and
  fine.

---

### Option C — operator workaround (complementary, not exclusive): set `max_action_executing_timeout_s`

Set `max_action_executing_timeout_s` in the production config to a
finite value (e.g. 600 s). This activates the third corner of the
composite invariant, providing an upper bound regardless of client
listener presence. **Note this only helps if the listener is polling at
all** — `max_executing_timeout` is checked inside
`should_timeout_operation` which is reachable only from the listener
loop.

So Option C ALONE does not fix #384; it must be combined with Option A
or B.

**Files to modify:**
- `/home/user/fl/bld/infra/nativelink/prod-server.json5` — add
  `max_action_executing_timeout_s: 600` to the SimpleSpec block.

**Risk profile (TRIVIAL):**
- Reduces the worst-case wedge from "forever" to 600 s, but only if
  someone is polling.

---

## Recommended option: A + C

- Option A is small, low-risk, and structurally closes the loop. It is the
  minimum change that makes the composite invariant satisfiable.
- Option C complements it by providing an absolute ceiling that operators
  can tune, and surfaces a real-time signal at lower latency than the
  default `worker_timeout_s = 30 s`.
- Option B is a cleaner long-term refactor but is not necessary today;
  Option A subsumes its safety contribution at lower implementation cost.

## Test plan

### Production-composition regression test (mandatory)

`nativelink-scheduler/tests/simple_scheduler_executing_sweeper_test.rs`:

```
test: scheduler_evicts_orphaned_executing_actions_when_no_listener
  setup:
    - Construct SimpleScheduler with worker_timeout_s = 30,
      no_event_action_timeout = 30, max_action_executing_timeout = 0
      (matching production defaults).
    - Register a healthy worker (sends keepalives every 1 s).
    - Use add_action(client_op_id, action_info) to add an action.
    - Wait for do_try_match to dispatch (poll until stage=Executing).
    - DROP the returned ActionStateResult listener immediately.
    - DO NOT subscribe via filter_operations.
  assertion:
    - Within tokio::time::timeout(120 s) the action transitions out of
      Executing. The expected terminal stage is either Completed (if
      the worker returns) or Queued (if re-queued via UpdateWithError).
    - Specific message in panic: "scheduler-driven Executing sweeper did
      not fire — action remains Executing"
  mutation step:
    - Comment out the `spawn!("simple_scheduler_executing_sweeper", ...)`
      line. Test must red-fail with the bespoke message above (NOT a
      generic tokio::time::Elapsed which would mask the bug).
```

The mutation step is mandatory per CLAUDE.md "Tests" section —
otherwise a refactor that accidentally removes the sweeper will not be
caught.

### Field test on buildcache

Once Option A ships:
- Reproduce: SIGTERM nativelink during a busy build. Confirm any
  actions dispatched during the +30 s window after restart eventually
  re-queue or complete within `2 * no_event_action_timeout = 60 s` even
  if the original Bazel client is killed. Observable via
  `journalctl --namespace=nativelink | grep "OperationId .* timed out
  after"` — the existing warn-level log at `simple_scheduler_state_manager.rs:229`
  is the visible signal.

## Composite-invariant interactions to audit

1. **Worker-eviction path (`immediate_evict_worker`).** The new sweeper
   may race with worker-eviction-driven re-queue if the worker
   disconnects at the same moment. Both paths converge on
   `update_operation` which is version-conflict-safe; second writer
   sees `Code::Aborted` and bails. No double-counting.

2. **Per-action client listener.** If a client listener IS polling and
   the new sweeper also fires, both will call `timeout_operation_id`.
   Same idempotency argument applies. The first writer wins.

3. **`max_action_executing_timeout_s`.** Today disabled in production.
   If Option C is also adopted, the sweeper checks `max_executing_timeout`
   first via `should_timeout_operation`, so the absolute ceiling is
   honored.

4. **`max_job_retries`.** When the sweeper fires
   `timeout_operation_id`, the standard re-queue flow runs and
   increments `attempts`. After `max_job_retries` (default 3), the
   action is marked Completed-with-error rather than re-queued, exactly
   like today.

5. **Boot-epoch wipe (`worker_api_server.rs:520-600`).** Untouched.
   Boot-epoch wipe today does not interact with action assignments; the
   fix does not change that.

## Open questions for user

1. **Sweeper interval.** Recommended `no_event_action_timeout / 2`
   (15 s with default config). Could be `no_event_action_timeout / 4`
   for faster recovery, at the cost of more wakeups against
   `awaited_action_db`. Choose: 15 s (default), 7.5 s (aggressive),
   30 s (conservative), or configurable knob?

2. **Should the sweeper also re-dispatch immediately on detected
   timeout?** Today `timeout_operation_id` re-queues the action;
   `do_try_match` then picks it up on its next wake-up
   (`task_change_notify`). If we want zero-latency re-dispatch, the
   sweeper can `worker_change_notify.notify_one()` after each timeout.
   Recommendation: yes, notify; cheap and reduces tail-latency on
   recovery.

3. **`max_action_executing_timeout_s` value.** Recommend 600 s for
   long-running compile actions. The action's own deadline (in
   `Action.timeout`) is a separate concern. What is the longest
   legitimate single action duration in this build cluster? If unknown,
   start at 1800 s and tighten after measurement.

4. **Should we also add metrics?** A counter for "actions timed out by
   the new sweeper" would make this gap visible operationally.
   Suggestion: `executing_sweeper_timeouts_total` with labels for the
   reason (`worker_dead`, `max_executing_exceeded`,
   `no_event_timeout`). Trivial; recommend yes.

5. **Bazel-side reconnect.** Out of scope for nativelink, but the
   underlying trigger is "Bazel did not re-issue WaitExecution after
   server restart." If Bazel has a known bug here, file separately.
   Nativelink's correct response is to be self-healing regardless.
